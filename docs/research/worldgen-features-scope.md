# 26.3 overworld feature pipeline: scope for the Java clone

Read-only scoping. Sources: the 26.3 client jar (`javap -c -p`), the extracted `data/minecraft/worldgen/**`, and the repo at `src/main/java/com/example/worldgen/**`. Every claim names its class or file. "UNVERIFIED" marks anything not read from bytecode or data. Tables are generated by script from the data (exact counts); prose was written from the bytecode dumps. Date of the pass: 2026-10-19.

Scope: the 56 biomes reachable in `OverworldBiomeBuilder` (all ids of `Biomes.java` except the 11 nether/end/void ids: `the_void`, `nether_wastes`, `soul_sand_valley`, `crimson_forest`, `warped_forest`, `basalt_deltas`, `the_end`, `small_end_islands`, `end_midlands`, `end_highlands`, `end_barrens`). All 56 have the same carver list (see the carvers report).

## 0. What differs from the 1.21-era design (all confirmed in this jar)

- There is no `ConfiguredFeature` wrapper any more: `PlacedFeature` is `record(Holder<Feature> feature, List<PlacementModifier> placement)` and `Feature` is an interface (`codec()`, `place(WorldGenLevel, ChunkGenerator, RandomSource, BlockPos)`). The JSON in `worldgen/feature/*.json` is the flat feature body with a `type` key (no `config` object). Classes: `levelgen/placement/PlacedFeature`, `levelgen/feature/Feature`, `levelgen/feature/FeatureTypes` (registry bootstrap).
- There is no `random_patch`, `flower` or `no_bonemeal_flower` feature in the data. Patches are a `simple_block` or `block_column` feature plus placement (`count`, `offset` with trapezoid x/y/z, `block_predicate_filter`); see `placed_feature/patch_bush.json`. New feature types: `overlay`, `sequence`, `template`, `fallen_tree`, `coral_tree`, `coral_claw`, `speleothem`, `speleothem_cluster`, `spike`, `weighted_random_selector`, `random_boolean_selector`, `simple_random_selector`, `random_selector`. The old `lake` has a new config (`barrier`, `fluid`, `can_place_feature`, `can_replace_with_*`).
- `PlacementModifier.modify(ctx, random, pos, Consumer<BlockPos>)` replaces `Stream<BlockPos> getPositions`. Placement is run by the new class `levelgen/placement/FeaturePlacer` (section 1.4).
- Trees gained `poplar` trunk/foliage placers, `fallen_tree`, and new decorators (`pale_moss`, `creaking_heart`, `shelf_mushroom`, `attached_to_logs`, `attached_to_leaves`, `place_on_ground`, `alter_ground`).
- New overworld content in these biomes: the `sulfur_caves` biome (blocks sulfur, cinnabar, potent_sulfur, sulfur_spike), `dappled_forest` (poplar leaf litter, fallen poplar trees), `pale_garden`, firefly bush, `bush`, `red_shrub`, `cactus_flower`, `wildflowers`, `leaf_litter`, dry grass.
- Biome JSON has an `attributes` object and a `carvers` list; `features` is an array of 11 lists of placed-feature ids.

## 1. Vanilla decoration pipeline (exact)

### 1.1 Steps

`GenerationStep$Decoration` (enum order, `levelgen/GenerationStep`): 0 RAW_GENERATION, 1 LAKES, 2 LOCAL_MODIFICATIONS, 3 UNDERGROUND_STRUCTURES, 4 SURFACE_STRUCTURES, 5 STRONGHOLDS, 6 UNDERGROUND_ORES, 7 UNDERGROUND_DECORATION, 8 FLUID_SPRINGS, 9 VEGETAL_DECORATION, 10 TOP_LAYER_MODIFICATION. A biome's `features` is an array of 11 lists, index = step ordinal (`BiomeGenerationSettings.features()` is `List<HolderSet<PlacedFeature>>`).

### 1.2 `ChunkGenerator.applyBiomeDecoration(WorldGenLevel, ChunkAccess, StructureManager)` (833 bytes), in order

1. `pos = chunk.getPos()`; return at once if `SharedConstants.debugVoidTerrain(pos)`.
2. `origin = SectionPos.of(pos, level.getMinSectionY()).origin()` = block (pos.minBlockX, level.minY, pos.minBlockZ). **Every feature starts from this one origin**; the x/z offsets come from `in_square` randomness.
3. `structuresByStep` = structure registry grouped by `Structure.step().ordinal()`. `featuresPerStep` = memoised supplier (1.3).
4. `random = new WorldgenRandom(new XoroshiroRandomSource(RandomSupport.generateUniqueSeed()))`. The wrapped source is **Xoroshiro**. `WorldgenRandom.next(bits)` is `(int)(xoroshiro.nextLong() >>> (64 - bits))` for a non-legacy wrapped source, so every `nextInt/nextFloat/nextDouble/nextBoolean` consumes one full Xoroshiro `nextLong`, and `WorldgenRandom.nextLong()` (inherited `LegacyRandomSource.nextLong` = `(next(32) << 32) + next(32)`) consumes two. `WorldgenRandom.setSeed(long)` forwards to the wrapped source, so every seed below goes through Xoroshiro seeding. The repo already ports this class: `worldgen/random/WorldgenRandom.java`.
5. `decorationSeed = random.setDecorationSeed(level.getSeed(), origin.x, origin.z)`: `setSeed(levelSeed); a = nextLong() | 1; b = nextLong() | 1; seed = (long)x * a + (long)z * b ^ levelSeed; setSeed(seed); return seed` (`WorldgenRandom.setDecorationSeed`, 45 bytes).
6. `possibleBiomes`: for every chunk of `ChunkPos.rangeClosed(pos, 1)` (3x3) take `level.getChunk(x,z)` and add every palette entry of every section's `getBiomes()` (`PalettedContainerRO.getAll`) to an `ObjectArraySet`; then `retainAll(biomeSource.possibleBiomes())`. This is a set of biomes, not a per-position choice: the feature lists of every biome present in the 3x3 area are merged.
7. For `stepIndex` in `0 .. max(11, featuresPerStep.size()) - 1`:
   - a. Structures first (if `sm.shouldGenerateStructures()`): for each structure of that step (counter `structureIndex` from 0): `random.setFeatureSeed(decorationSeed, structureIndex, stepIndex)` then `StructureStart.placeInChunk`. Out of scope here.
   - b. Features (if `stepIndex < featuresPerStep.size()`): `ids = new IntArraySet()`; for every biome in `possibleBiomes`: `settings = generationSettingsGetter.apply(biome).features()`; skip if `stepIndex >= settings.size()`; for each `PlacedFeature pf` in `settings.get(stepIndex)` add `featuresPerStep.get(stepIndex).indexMapping().applyAsInt(pf)`. Then `toIntArray()` and `Arrays.sort`.
   - c. For each sorted index `idx`: `pf = featuresPerStep.get(stepIndex).features().get(idx)`; `random.setFeatureSeed(decorationSeed, idx, stepIndex)`; `featurePlacer.placeWithBiomeCheck(pf, random, origin)` (one `new FeaturePlacer(level, this)` per chunk).
8. `WorldgenRandom.setFeatureSeed(decorationSeed, index, step)` = `setSeed(decorationSeed + index + 10000 * step)` (20 bytes). `index` is the position in the sorter's per-step list, not the position in one biome's list.

### 1.3 `FeatureSorter.buildFeaturesPerStep(biomes, getter, true)` (`world/level/biome/FeatureSorter`, 658 bytes)

- Called once (memoised) from the `ChunkGenerator` constructor with `List.copyOf(biomeSource.possibleBiomes())` and `biome -> generationSettings(biome).features()`. The biome iteration order is **the order of `biomeSource.possibleBiomes()`**, the distinct biomes in `Climate.ParameterList.values()` order. The repo mirrors that already in `worldgen/biome/MultiNoiseBiomeSource.possibleBiomes()` (a `LinkedHashSet`). The order changes the tie-breaks below, so it must be exact.
- Per biome, the `features()` lists are flattened (step by step) into `FeatureData(featureIndex, step, PlacedFeature)`. `featureIndex` is a first-encounter counter per distinct `PlacedFeature` (`Reference2IntOpenHashMap.computeIfAbsent`; counter shared across biomes); `step` is the list index. Comparator: `comparingInt(FeatureData::step).thenComparingInt(FeatureData::featureIndex)` (targets confirmed with `javap -v` bootstrap methods).
- A directed graph `TreeMap<FeatureData, Set<FeatureData>>` gets, for each biome, an edge from each flattened feature to the next one in that biome (consecutive pairs, across step boundaries). DFS in `TreeMap` key order with `Graph.depthFirstSearch(edges, visited, inProgress, postOrderConsumer, node)`; the post-order list is reversed (`Collections.reverse`). On a cycle, with the boolean argument `true`, it retries while removing biomes one at a time and finally throws `IllegalStateException("Feature order cycle found")`.
- Result per step `s`: `StepFeatureData(features = reversed list filtered to step s, indexMapping = feature -> position in that list)`. **That position is the `index` of `setFeatureSeed`.**
- For the clone: run it over exactly the 56 biomes in parameter-list order, using the real `features` arrays of the biome JSON.

### 1.4 `FeaturePlacer` (new class, `levelgen/placement/FeaturePlacer`; private `place(pf, random, pos, boolean)` is 395 bytes)

- `placeWithBiomeCheck(pf, random, origin)` = `place(..., true)`; `place(pf, random, origin)` = `place(..., false)`. With `true` the `PlacementContext` carries `Optional.of(pf)` as `topFeature`. The `biome` modifier (`BiomeFilter.shouldPlace`) throws when it is empty, otherwise returns `generator.getBiomeGenerationSettings(level.getBiome(pos)).hasFeature(topFeature)`: the top-level feature must be in the feature lists of the biome **at the candidate position**.
- `feature = pf.feature().value()`; `modifiers = pf.placement()`. If `modifiers` is empty: `return feature.place(level, generator, random, origin)`.
- Otherwise an explicit stack: `positions = [origin]`, `modifierIndices = [0]`, `placed = false`. While `positions` is not empty: `pos = positions.removeLast()`, `idx = modifierIndices.removeLast()`; `modifiers[idx].modify(ctx, random, pos, modifiedPositions::add)` (all outputs of one modifier for one input are produced eagerly and in order, consuming `random` in that order); `next = idx + 1`. If `next < modifiers.size()`: push the outputs **in reverse order** (last output first) with index `next`, so the first output is popped first (depth first, input order preserved). Else (last modifier): for each output in order `placed |= feature.place(level, generator, random, outPos)`. Then `modifiedPositions.clear()`.
- Random order consequence: modifier 0 for the origin; then the whole remaining chain for output 1 (modifiers 1..n, then the feature), then output 2, and so on. Whether this is identical to the pre-26.3 lazy `Stream.flatMap` order is UNVERIFIED and irrelevant: port this stack algorithm.
- `PlacementModifier` is a `PlacementFilter` (`shouldPlace(ctx, random, pos)`; emits `pos` or nothing), a `RepeatingPlacement` (`count(random, pos)` copies of `pos`; the count is sampled once per input) or a direct `modify`. `PlacementContext` exposes `getHeight(Heightmap.Types, x, z)` = `level.getHeight(...)` (the **live** heightmap of the region being generated, already changed by earlier features), `getBlockState(pos)`, `getMinY()`, `getLevel()`, `topFeature()`, `generator()`.

Semantics read from bytecode for the modifiers used most (sizes for all in 2.3):

| modifier | exact behaviour (bytecode) |
|---|---|
| `in_square` | `x += random.nextInt(16); z += random.nextInt(16)` (x drawn first), y unchanged (`InSquarePlacement.modify`, 52 bytes) |
| `count` | repeat the input position `count.sample(random)` times |
| `rarity_filter` | pass iff `random.nextFloat() < 1.0f / chance` (`RarityFilter`, 22 bytes) |
| `random_chance` | pass iff `random.nextFloat() < chance` |
| `height_range` | `pos.atY(height.sample(random, worldGenerationContext))` |
| `heightmap` | `y = ctx.getHeight(type, x, z)`; emit `(x, y, z)` only if `y > ctx.getMinY()` |
| `surface_water_depth_filter` | pass iff `WORLD_SURFACE height - OCEAN_FLOOR height <= max_water_depth` |
| `offset` | `pos.offset(x.sample(random), y.sample(random), z.sample(random))`, drawn in that order |
| `biome` | see 1.4 |
| `block_predicate_filter` | `predicate.test(level, pos)` |
| the rest | `noise_based_count`, `noise_threshold_count`, `surface_relative_threshold_filter`, `environment_scan`, `count_on_every_layer`, `cuboid`, `randomly_selected`, `fixed_placement`: only class sizes were taken; semantics UNVERIFIED until the class is read at port time |

### 1.5 What the clone must host to run this loop

- A `WorldGenLevel`-like view over a 3x3 chunk neighbourhood: read/write block states, `getBiome(blockPos)`, `getHeight(type, x, z)` over **live heightmaps** (types used by placements: `WORLD_SURFACE`, `OCEAN_FLOOR`, `MOTION_BLOCKING`, `MOTION_BLOCKING_NO_LEAVES`; terrain uses `WORLD_SURFACE_WG`, `OCEAN_FLOOR_WG`). Chunk pyramid (`ChunkPyramid.GENERATION_PYRAMID`): FEATURES requires `STRUCTURE_STARTS` radius 8 and `TERRAIN` radius 1 and has `blockStateWriteRadius(1)`. The repo currently spills tree blocks to neighbours via `World.spill`, a different mechanism.
- Block states with properties (log axis, leaves distance/persistent/waterlogged, vine faces, slab type, doors...). `BlockType` is a flat enum of ids without properties (class comment of `world/BlockType.java`; `TreePlanner` doc: "logs carry no axis").
- Block tags (`data/minecraft/tags/block/**`, 300 files), `BlockPredicate` and `RuleTest` evaluation.
- Light is needed by `freeze_top_layer` (`SnowAndFreezeFeature`, 258 bytes; which light layer is UNVERIFIED); whether `monster_room` needs light is UNVERIFIED.

### 3.4 Carvers and the aquifer

Carvers no longer name blocks (see the carvers report): `cave.json`, `cave_extra_underground.json`, `canyon.json`, `nether_cave.json` have no `replaceable`/`lava_level` fields. Carved cells are recorded in a `CarvingMask` and later replaced via `Aquifer.computeSubstance(x,y,z,0.0)` (stone-to-air/water/lava per aquifer) and `BlockTags.UNCARVABLE`; grass/mycelium over dirt is restored from the material rule. Blocks involved: `air`, `water`, `lava` (fluid picker: lava below y = min(-54, sea level), else default fluid `water` at sea level), `stone` (default block), `grass_block`, `mycelium`, `dirt`, and the surface material result. All are in the table above or in the sibling reports.

## 5. Proposed port order (smallest verifiable slices)

Verification method for every slice (the project's established "oracle" method): run the real 26.3 classes from `client.jar` against a stub `WorldGenLevel` that records `setBlock`/`getHeight` calls, and compare the recorded `(pos, state)` sequence and the final `random` state with the Java clone for several seeds/chunks. The random-consumption order is the thing that breaks silently, so compare after every feature, not only at the end.

## 6. Open items and risks

- UNVERIFIED: semantics of `noise_based_count`, `noise_threshold_count`, `surface_relative_threshold_filter`, `environment_scan`, `count_on_every_layer`, `cuboid`, `randomly_selected`, `fixed_placement`; every `Feature.place` body (only sizes were taken here); the exact light layer read by `freeze_top_layer`.

- The legacy generator's ad hoc plants/trees/ores are to be deleted once each slice matches the oracle (project rule: no fake code beside the real port).
- `BlockType` has only 42 of the 159 blocks the features, surface rules, ore veins and templates write (section 3.1), and no block-state properties; this is the main engine prerequisite.
